# 修复公告详情报错和首页公告栏不显示 - 实施计划

## Bug 分析

### Bug 1: 首页公告栏不显示

**根因**: `AjaxResult::success()` 对关联数组做了**扁平化处理**。

追踪 `AjaxResult::success()` 的逻辑（第 23-29 行）：
```php
if (is_array($data)) {
    $data = self::convertToCamelCase($data);
    if (self::isAssociative($data)) {
        $result = array_merge($result, $data);  // ← 扁平化！
    } else {
        $result['data'] = $data;
    }
}
```

Service 返回 `['list' => $notices, 'unreadCount' => $unreadCount]` 是关联数组，`isAssociative` 返回 true，所以 `array_merge` 将 `list` 和 `unreadCount` 合并到了顶层。

**实际响应**：
```json
{ "code": 200, "msg": "操作成功", "list": [...], "unreadCount": 3 }
```

**前端期望**：
```json
{ "code": 200, "msg": "操作成功", "data": { "list": [...], "unreadCount": 3 } }
```

前端代码 `res.data` 取到的是 `undefined`，所以公告栏始终为空。

### Bug 2: 查看公告详情报"系统未知错误"

**根因**: `isRead` 动态属性在序列化时丢失。

Service 中通过 `$notice->isRead = true` 设置的动态属性**不在 Model 的 `$attributes` 中**。`AjaxResult::success()` 调用 `convertToCamelCase()` 时，对 Model 执行 `toArray()`，**动态属性不会被包含**。

结果：前端拿到的通知项没有 `isRead` 字段，`markNoticeRead` 可能因 `noticeId` 类型问题或路由匹配问题导致后端 500 错误。

同时 APP 端详情页使用 `onMounted` + `getCurrentPages()` 获取页面参数，而非 uni-app 标准的 `onLoad` 生命周期，可能导致参数获取失败。

## 修复步骤

### 步骤 1：后端 - 修复 `isRead` 序列化丢失问题

**文件**: `webman/app/service/SysNoticeService.php`

将 `isRead` 动态属性改为通过 Model 的 `append` 机制或直接在返回数据中手动添加，确保 `toArray()` 时包含该字段。

方案：在 `listTop` 方法中，将 Collection 转为数组后手动添加 `isRead` 字段：

```php
public function listTop($userId)
{
    $notices = SysNotice::where('status', '0')
        ->orderBy('create_time', 'desc')
        ->limit(10)
        ->get();

    $readIds = SysNoticeRead::where('user_id', $userId)->pluck('notice_id')->toArray();

    $unreadCount = 0;
    $list = [];
    foreach ($notices as $notice) {
        $isRead = in_array($notice->notice_id, $readIds);
        $item = $notice->toArray();
        $item['is_read'] = $isRead;
        $list[] = $item;
        if (!$isRead) {
            $unreadCount++;
        }
    }

    return [
        'list' => $list,
        'unreadCount' => $unreadCount
    ];
}
```

### 步骤 2：前端 - 修复 `listTop` 响应解析（3 个文件）

由于 `AjaxResult::success()` 会将关联数组扁平化到顶层，`list` 和 `unreadCount` 在响应的顶层，不在 `res.data` 下。

**文件 1**: `front/src/layout/components/HeaderNotice/index.vue`

```js
// 修改前
const data = res.data || {}
const list = Array.isArray(data.list) ? data.list : ...

// 修改后：优先从 res.data 取，取不到则从 res 顶层取
const list = Array.isArray(res.data?.list) ? res.data.list
           : Array.isArray(res.list) ? res.list
           : (Array.isArray(res.data) ? res.data : [])
const unreadCount = res.data?.unreadCount ?? res.unreadCount ?? list.filter(n => !n.isRead).length
```

**文件 2**: `front/src/views/index.vue` — 同上

**文件 3**: `AppV3/src/components/home/NoticeBar.vue` — 同上

### 步骤 3：APP 端 - 修复详情页参数获取

**文件**: `AppV3/src/pages/system/notice/detail.vue`

将 `onMounted` + `getCurrentPages()` 改为 uni-app 标准的 `onLoad` 生命周期：

```js
import { onLoad } from '@dcloudio/uni-app'

onLoad((options) => {
  const noticeId = options?.noticeId
  if (noticeId) {
    loadDetail(noticeId)
  }
})
```

### 步骤 4：APP 端 - 修复 HeaderNav 的 unreadCount 解析

**文件**: `AppV3/src/components/home/HeaderNav.vue`

同样需要适配 `AjaxResult` 扁平化后的响应格式，从 `res` 顶层取 `unreadCount`。
