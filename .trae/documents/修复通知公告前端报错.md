# 修复通知公告前端报错 - 实施计划

## Bug 分析

### Bug 1: Web 端 `TypeError: noticeList.value.filter is not a function`

**根因**: 后端 `listTop` 接口现在返回 `{ list: [...], unreadCount: N }` 格式，前端解析逻辑 `data.list || data || []` 有问题。

当 `data = { list: [...], unreadCount: N }` 时：
- `data.list` 是数组 → 正常返回数组 ✅

但当 `data.list` 为 `undefined`（后端异常情况）时：
- `data.list || data` → 返回 `data` 对象 `{ list: undefined, unreadCount: N }`，不是数组 ❌
- 后续 `.filter()` 调用报错

**涉及文件**（3 处相同问题）：
1. `front/src/layout/components/HeaderNotice/index.vue` 第 61 行
2. `front/src/views/index.vue` 第 1173 行
3. `AppV3/src/components/home/NoticeBar.vue` 第 30 行

**修复方案**: 使用 `Array.isArray()` 确保始终得到数组：
```js
const data = res.data || {}
const list = Array.isArray(data.list) ? data.list : (Array.isArray(data) ? data : [])
noticeList.value = list
```

### Bug 2: APP 端循环公告列表不见了

**根因**: 与 Bug 1 相同的数据解析问题。`res.data.list || res.data || []` 当 `res.data` 是对象时，`res.data` 不是数组，`.map()` 调用失败，被 `.catch(() => {})` 静默吞掉，`noticeList` 保持为空数组 `[]`，`v-if="noticeList.length > 0"` 隐藏了组件。

**修复方案**: 同 Bug 1，确保解析出数组后再 `.map()`。

### Bug 3（潜在）: 后端 `unreadCount` 计算可能不准确

**根因**: `$notices->where('isRead', false)` 中 `isRead` 是动态属性（非模型 `$attributes`），Laravel Collection 的 `where()` 使用数组访问，动态属性可能无法被正确检索。

**修复方案**: 在 Service 层用 PHP 原生过滤替代 Collection 的 `where()`：
```php
$unreadCount = $notices->filter(fn($n) => !$n->isRead)->count();
```
